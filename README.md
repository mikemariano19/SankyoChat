# Sankyo Chat

A team chat app made of plain HTML, CSS and JavaScript. It runs with no internet and no server: you copy the folder to the office shared drive, and the shared `data` folder carries messages between PCs.

**Requirements:** Microsoft Edge or Google Chrome, version 110 or newer. Nothing gets installed.

## Deploying

1. Copy this whole `SankyoChat` folder to the share, for example `\\fileserver\Shared\SankyoChat\`.
2. Permissions:
   - App files (`index.html`, `check.html`, `css`, `js`, `assets`): **read-only** for staff. Only you or IT can change them. Anyone who can edit the code could make it capture passwords.
   - `data` folder: **Modify** for the staff group only.
3. Turn on Previous Versions (shadow copies) for the share, or copy `data` daily. A copy of `data` is a full backup, and DMs stay encrypted in it.
4. Give staff a desktop shortcut to `\\fileserver\Shared\SankyoChat\index.html`, set to open in Edge or Chrome.
5. **Open the app yourself first.** The first person to connect an empty `data` folder creates the workspace and becomes the **super admin**. You'll also set a **security question**: if you forget your password, pick your name on the sign-in screen and click **Forgot password?** to choose a new one (your messages stay readable). Change the question any time in ⚙ → **Security question**. Treat the answer like a second password, because anyone with the data folder can try guesses. Without the question, nobody can reset the super admin's password. Appoint admins later in ⚙ → Admin settings → People → **Make admin**.
6. Optional: in the app, open ⚙ → Admin settings → App files → **Check app files**, pick the `SankyoChat` folder, and click **Save as trusted fingerprint**. Later you can re-check whether anyone changed the code.

When a PC has problems, open `check.html`. It tests the browser, folder access (it writes, reads and deletes a small file), encryption and notifications.

### Updating

1. Super admin: ⚙ → Admin settings → Settings → **Update the app** → **Start update**. Within about 5 seconds every other app (1.9 or newer) shows "Sankyo Chat is being updated" and stops reading and writing the share.
2. Copy the new files over the app folder (raise `APP_VERSION` in `js/version.js`, and add an entry to `NEWS` in `js/chat.js` for the What's new pop-up). Never copy anything over `data`.
3. Click **Finish update** (in the red banner). Everyone's app reloads with the new files.

Apps older than 1.9 don't know update mode. For the first rollout of 1.9, copy the files, then ask everyone to reload (they also see "A new version is available. Reload" within 5 minutes).

## How it works

| File | Role |
| --- | --- |
| `js/store.js` | The only module that touches the shared folder (File System Access API) |
| `js/crypto.js` | Web Crypto: ECDSA P-256 signatures, ECDH P-256 + HKDF, AES-GCM 256, PBKDF2-SHA256 at 600,000 rounds |
| `js/account.js` | Workspace, profiles, sign-in, admin actions, feedback inbox |
| `js/sync.js` | Channels, messages, polling, presence, 7-day DM retention, search, export |
| `js/notify.js` | Notification inbox (bell), group join requests and suggestions |
| `js/ui.js` | DOM helpers, dialogs, message formatting, setup screens |
| `js/chat.js` | Main chat view and in-chat dialogs |
| `js/app.js` | Start-up, routing, theme, notifications, idle and auto-lock, update check |
| `js/emoji.js` | Bundled emoji list |
| `js/check.js` | The compatibility check page |

- **Every write creates a new file** (`channels/<id>/<UTC day>/<ts>_<user>_<rand>.json`). No two people ever write the same file. Edits, deletes and reactions are separate signed event files (`*.ev.json`).
- **Polling:** the open conversation is listed every 2 s. Every 5 s the app reads each person's small `presence/<id>.json` file, whose `lastPost` map shows which conversations changed, and then lists only those. A heartbeat is written every 10 s. Polling pauses when the window has been hidden for 5 minutes.
- **Signatures:** every message, event, profile, channel and `workspace.json` is signed. Messages that fail the check are hidden behind "Unverified sender". Forged edits and reactions are ignored.
- **DMs and group DMs:** text, mentions, replies and attachments (including file names) are encrypted. 1:1 keys come from ECDH between the two people. A group DM uses a random key, wrapped once for each member. Expired DM files and their attachments are deleted hourly by members, and by the admin's app for every DM.
- **Keys** are encrypted with your password and stored in `users/<id>.keys.json`. Passwords are never stored. "Keep me signed in" keeps non-extractable keys in this browser only.
- **Kept on each PC only:** the folder permission, last-read positions, theme and sound settings, and a cache of channel messages (files never change once written, so caching them is safe).

## Where it differs from the requirements doc

- **Classic scripts, not ES modules.** Edge and Chrome refuse to load `type="module"` scripts from `file://` pages, so every file attaches to one global `SC` namespace instead. There is still no build step.
- **"Keep me signed in" turns off auto-lock on that PC.** Otherwise the checkbox would do nothing, because auto-lock would sign people out anyway. The checkbox says to use it only on a PC nobody else uses. The admin sets the auto-lock time (default 30 minutes; "Never" is allowed).
- **Super admin and admins** (the requirements doc had one admin). The workspace creator is the **super admin**. Only they can appoint or remove admins, change workspace settings, check the app files, and read the feedback inbox, which is encrypted to their key alone. **Admins** can create, rename and archive channels, hide channel messages, and reset passwords or remove regular staff. They can never touch the super admin or other admins, and nobody can read DMs.
  - The admin list lives in `workspace.json`, which only the super admin's key can sign.
  - Each admin action is its own file in `data/admin/`, signed by the admin who took it. Every app checks the signer against that list and ignores anything else.
  - When an admin is removed, actions they took while they were admin stay in effect. Admin settings → Activity shows who did what.
- **Only admins can create channels** (FR-05 said anyone could). Everyone else's app hides the "+" button, and every app ignores channel folders on the share unless an admin signed them. Everyone can still start direct messages, and anyone can create a named **group chat** (sidebar → Group chats → +) with up to 50 people. Group chats are encrypted like DMs, including their name, and follow the same 7-day retention. The creator can rename the group, add people and remove people later (Details → Rename / Add people / Remove). Removing someone gives the group a new key generation (`meta.gen`), wrapped only for the people who stay; older generations are kept in `meta.past` so members can still read earlier messages. Files a removed person writes after their removal are shown as "Unverified sender". Members can **Leave group** from Details: they write a signed `leave/<userId>.json` in the group folder (members can't sign `meta.json`), everyone's app hides them at once, and the creator's app then removes them for real, which rotates the key. The creator can't leave their own group. New members get the existing group key, so they can read what is still in the group (7 days at most). Only the creator re-signs the group's `meta.json` (with a higher `rev`), so it still has a single writer.
- **Group admins.** A group's creator can make members **group admins** (Details → Make admin). Group admins can rename the group, add people and remove regular members; only the creator chooses admins or removes an admin, and nobody can remove the creator. The admin list is a separate block in `meta.json` signed by the creator alone, and `meta.json` itself may be signed by the creator or a listed admin (`meta.by`). Leaves are processed by the creator's app, or by a group admin's app if the creator hasn't done it within 10 minutes. If two admins change a group at the same moment, the later save wins.
- **Read receipts.** DMs and groups show "Seen" / "Seen by …" under your newest message. Each person's presence file carries `seen` (the newest message they've read per conversation). Anyone can turn this off in ⚙ → Read receipts; like WhatsApp, they then stop seeing other people's receipts too. Presence files aren't encrypted, so someone browsing the share can see when a DM was read.
- **Announcements.** They have their own channel at the top of the sidebar, where everyone can read past announcements (kept for a year). Admins post with **New announcement** there. Each one is a signed file in `data/announcements/` (ignored unless the signer was an admin at the time). A new one pops up over whatever is open; closing the pop-up counts as seen, and opening the channel marks everything in it as seen. Posting or withdrawing also sets `lastPost.announcements` in the admin's presence file, so other apps pick it up within about 5 seconds without a reload. Acknowledgements go into each person's presence file (`acks`), so admins can see who hasn't read it. Announcements aren't encrypted. Withdrawing one deletes its file, so it just disappears (no "deleted" marker).
- **Private channels.** Admins can create a channel that's invite-only (sidebar → Channels → + → Private), up to 50 people. Underneath it's a group (`meta.channel = true` in the signed `meta.json`), so it's end-to-end encrypted, name and description included, and only invited people can see or read it, other admins included. Unlike group chats it keeps its history: messages carry `expires: 0` and the hourly cleanup skips it. The creator and channel admins invite and remove people; people invited later also get the older key generations, so they can read the whole history. An existing public channel can't be locked after the fact, because its messages are plain files on the share. **Make private** (Details) instead creates a private channel with the same name for the people chosen, and archives the public one.
- **Private announcements.** Admins can send an announcement to chosen people instead of everyone. "Add everyone in…" fills the list from any private channel or group the admin is in, so existing teams act as announcement groups. The title and text are encrypted with a random key wrapped for each recipient. The recipient list (`to`) is readable on the share; the content isn't.
- **Notifications (1.9).** The bell in the sidebar header collects mentions, replies, @here, being added to or removed from a group, being made a group admin, and request results. Group admins also get join requests, suggestions and "left the group"; admins get people waiting for a group and new profiles; the super admin gets admin activity. Nothing is sent: each app works these out from files it can already read. Read-state is `notifRead` / `notifSeen` in each person's presence file, so it follows them to other PCs. Previews from encrypted conversations are never saved on the PC. ⚙ → Notification settings chooses what pops up and has Do not disturb.
- **Browse groups and requests (1.9).** A group chat or private channel can be listed (create dialog, or Details → List in Browse groups): `meta.listed = true` plus a signed `data/directory/<groupId>.json` with only its name, description and member count. Others ask to join from sidebar → Group chats → search. Members suggest someone from Details. Requests are signed files in `data/requests/<groupId>/` (suggestions are encrypted with the group key); the group admin who decides writes `<requestId>.status.json`. Approving runs the normal Add people. Requests expire after 14 days.
- **Admin audit for the super admin (1.9).** When an admin creates a named group chat or private channel, makes a channel private, or sends a private announcement, their app also writes `data/admin/audit/<id>.json`: kind and count in the clear, the name or title sealed to the super admin's key only. Message content is never included. These show in the bell (Admin activity) and in Admin settings → Activity.
- **Update mode (1.9).** `workspace.json` `maintenance = {on, ts, message}`, signed by the super admin. Other apps check it every 30 s, and within about 5 s through a presence hint (`lastPost['maint:all']`); they stop syncing and reload once it's off.
- **Real names (1.9).** Edit profile has an optional real name that only admins and the super admin can read. User records are plain files on the share, so it's sealed separately to each reader's key (`realName.to[userId]`): the person, the super admin and each admin. When the admin list changes, the person's app re-seals it the next time it runs, so a new admin sees "Not shared with you yet" until then, and a former admin's copy is removed.
- **New announcement → Send to (1.9).** Group chips (PICKUP GROUP, INPUT GROUP, then private channels and group chats) stay selected and show how many people they add; clicking again removes those people. A group with nobody accepted yet is disabled, and the dialog says how many people are still waiting for an admin to accept their group (they don't get it).
- **Private announcements stay inside the admin's group (1.9).** An admin can only send a private announcement to people in their own accepted group: the dialog shows only that group's chip and people (group chats only add their members from that group), the group view's "Send announcement to this group" button only appears on their own group, and `Y.postAnnouncement` refuses anyone outside it. An admin without an accepted group can only post to everyone. The super admin can send to anyone. Announcements to everyone are unchanged.
- **Announcement feeds (1.9).** The sidebar shows Announcements (everyone, plus private ones sent to people from both groups) and one feed per group: Announcements (PICKUP), Announcements (INPUT). Members and admins see their own group's feed; the super admin sees both. A private announcement whose recipients are all in one group is tagged with that group (`team` in the signed announcement file) and shows in that feed; older ones are placed by their recipients' current group. Each feed has its own unread badge; opening a feed marks only its announcements as seen, and pop-ups still appear for the others. Posting from a group feed preselects that group.
- **Editing announcements (1.9).** Edit and Delete appear when an admin hovers over (or tabs to) an announcement. The author can edit; `data/announcements/edits/<announcementId>.json` holds the newest title and text, signed by them (encrypted with the same key for a private one). Delete removes both files.
- **Groups: PICKUP GROUP and INPUT GROUP.** The sidebar's Groups section lists both, with member counts; clicking one shows its members (online first), and admins see who's waiting to be accepted there. Everyone must belong to one of these two groups (they are not group chats). The list is in `workspace.json` (`teams`, ids `t1`/`t2`); the super admin can rename them in Admin settings → Settings, and everyone stays in their group because people are stored by group id. People choose with two buttons when they create their profile (no typing); profiles made before groups existed are asked once at sign-in and can't skip it. The choice is stored in their own signed user record (`team`), but it only counts once an admin accepts it or sets a different group: an admin action `{type: 'team', target, team}` in `data/admin/`, signed and checked like the other admin actions. Groups are permanent: staff can't change their own, and only admins can move someone (Admin settings → People → Accept / Change). Until an admin has given someone a group, nothing limited to a group reaches them, so a wrong pick never shows them the other group's announcements. Admins see a "waiting for their group" banner. In a new private announcement, **Group name** sends it to everyone accepted in PICKUP GROUP or INPUT GROUP, or to the members of a private channel or group chat. People lists show five people at a time and scroll.
- **Admin guide.** ⚙ → Admin guide lists everything an admin (or the super admin) can do, with buttons to try each one. Admins get a one-time hint pointing to it.
- **One reaction per person per message.** Picking another emoji replaces your reaction; clicking your own removes it. Each person's reaction is whatever their newest reaction event says, so every PC agrees regardless of the order files arrive in.
- **Pinned messages.** In a group chat, the creator and group admins can pin messages; in channels, admins can. Pins are signed `pin` events, and every app ignores pins from anyone else. Pinned messages show in a bar under the conversation header.
- **Polls.** The super admin and admins can create a poll in any conversation they're in (the chart button next to the paper clip): a question, 2–10 options, and optionally "choose more than one". Everyone in the conversation can vote and change their vote; hovering an option shows who picked it. A poll is a message whose `poll` field only counts if its author was an admin at the time; votes are signed `vote` events (newest per person wins). Polls in DMs and groups are encrypted like any other message.
- **Attachments.** Two or more pictures in one message are shown together as one album grid (2 side by side, 3 as one large and two small, 4 or more as 2×2 with "+N" on the last tile), so they take about the height of one picture. Clicking a tile opens the viewer, where ← → or the arrows move through the whole album. Pictures waiting in the composer show as small thumbnails. Images open in an in-app viewer that can zoom (mouse wheel, + / − buttons or keys, double-click) and pan (drag). PDFs open in an in-app viewer that uses the browser's own PDF reader; this is why `index.html` allows `blob:` in `frame-src` and `object-src`. Other files are saved with "Save as…" instead of opening in a new tab, because downloads may be blocked and blob tabs from `file://` pages are unreliable.
- **Sign-in list.** The sign-in screen re-reads the share every 20 seconds, and hides anyone who was removed or whose key file is gone.
- **Mockups vs. requirements:** where they disagree, the requirements win: the name is Sankyo Chat, there's no Department field, the file limit is 5 MB (not 10 MB), and avatars are animals.
- **Not built:** the typing indicator (FR-24, "Could"). It would add many writes to the share.

## Known limits

- Anyone with write access to `data` can delete files. Signatures expose altered messages but can't prevent deletion, so keep backups.
- Anyone browsing the share can see who DMs whom and when (folder names and timestamps), file sizes, and channel messages.
- **Forgotten passwords (1.9).** Every profile must have a security question and a real name: both are required on Create profile, and existing staff get a "Finish your profile" dialog after signing in that can't be dismissed (only Sign out) until they set them. "Forgot password?" on the sign-in screen unlocks their keys with the answer, so they keep every message. A copy of their private keys is stored in `users/<id>.keys.json` wrapped with the answer (PBKDF2, like the password), so admins can't use it, but anyone with the data folder can try guessing answers: tell staff to treat it like a second password. If someone also forgets the answer, an admin reset is the last resort: it creates new keys, clears the old question, and their DMs from before the reset (7 days at most) can't be opened. The reset dialog spells out what is lost, says when the person has a question and should use Forgot password instead, and needs the admin to type the person's name to confirm. After a reset the person is asked for a new question and their real name again. The super admin can't be reset by anyone.
- Times come from each PC's clock. If clocks differ by a lot, messages can appear slightly out of order.
